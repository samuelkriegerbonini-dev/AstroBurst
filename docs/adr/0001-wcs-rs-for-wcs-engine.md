# Use wcs-rs for the WCS linear/projection math, but not its SIP support

AstroBurst's old WCS engine (`WcsTransform`, `src-tauri/src/core/astrometry/wcs.rs`) hand-rolled TAN/SIN/ARC/CAR projection math and never read the FITS `PC` matrix convention — silently wrong for ASDF/Roman-derived headers, which emit `PC`+`CDELT` instead of `CD`. We replaced the linear (CD/PC/CDELT) transform and celestial projection/deprojection with the [`wcs`](https://github.com/cds-astro/wcs-rs) crate (wcs-rs + mapproj, crates.io), which supports ~20 FITS projections and handles `PC` correctly, while keeping `WcsTransform`'s public API unchanged.

We do **not** use wcs-rs's own SIP distortion support, even though it exists: `mapproj` 0.4.0's SIP polynomial evaluator has a confirmed bug (it advances polynomial powers by repeated squaring instead of by degree), caught by cross-checking `pixel_to_world` output against astropy — it silently produces sky coordinates off by tens of degrees, not just imprecise ones, for any SIP-distorted header. This matches wcs-rs's own README admission that SIP support is "not tested." `WcsTransform::from_header` strips any `-SIP` CTYPE suffix before constructing the wcs-rs engine so this path never runs, and applies/inverts SIP with AstroBurst's own (pre-existing) polynomial math instead.

## Consequences

- If a future `wcs`/`mapproj` upgrade fixes the SIP bug, the `-SIP`-suffix-stripping workaround and the hand-rolled `sip_forward`/`sip_inverse` methods become optional, not mandatory — worth revisiting then, not before.
- `pixel_scale_arcsec`/`field_of_view` still compute from a CD matrix synthesized directly from the header rather than asking the engine, with astropy's precedence: PC×CDELT when any PC card is present, then CD with missing cards as 0 (a zero diagonal term becomes 1 when CD1_2 and CD2_1 are both 0, as wcslib's cdfix does), then CDELT+CROTA2. Files with a full CD matrix and no PC keep bit-identical numbers; files with both CD and PC, or with a partial CD matrix, now match astropy.

## Differential TAN inverse near the reference position

For TAN headers without explicit `LONPOLE`, `LATPOLE`, or `PV` projection parameters, and with the reference latitude strictly between the poles, the sky-to-plane calculation uses longitude and latitude differences before conversion to radians. The northward numerator uses `sin(delta_lat)` and `2 sin²(delta_lon / 2)` instead of subtracting products of absolute unit vectors. This preserves very small offsets around the reference meridian; the existing CD inverse, celestial-frame conversion, and SIP inverse still apply. Other projections, explicit projection parameters, and reference positions at the poles retain the wcs-rs path. The forward transform is unchanged.

The concrete trigger is the synthetic LIGHTSTACK D1 field. The former inverse added a transverse offset of `-2.8625e-10` pixel to the F277W/F444W crop centre. Applying the unchanged floor/ceil rule selected one extra column: a 46×46 crop and a 44×44 aligned product. A differential inverse restores the 45×46 crop and 44×43 product supported by the stored header coordinates and the independent LIGHTSTACK golden. The one-ulp latitude difference remains positive, so this does not snap either coordinate to an integer or modify crop rounding.

Regression coverage includes the one-ulp latitude case, longitude wrap near a pole, explicit projection options against Astropy coordinates, exact D1 reference-meridian crop bounds without a tie allowance, and the complete recipe from the original D1 files through PSF matching. The existing oracle tolerances and golden files are unchanged. This addresses the identified TAN cancellation case; it does not certify every projection or establish an uncertainty model for resampling covariance.
